# bank_transactions.csv — словарь данных и заметки для проекта

Синтетический, но реалистично «грязный» датасет банковских транзакций для
задачи бинарной классификации: `is_fraud` (0 — легитимная операция, 1 —
мошенническая/подозрительная).

- Строк: ~40 800 (из них ~0.4% — намеренные дубликаты)
- Клиентов: 2500
- Период: 2025-09-04 — 2026-09-03 (ровно год)
- Доля `is_fraud=1`: ~1.7% (после шума в метках)
- Кодировка: UTF-8 с BOM (`utf-8-sig`) — открывается в Excel без кракозябр

Данные сгенерированы `generate_dataset.py` с фиксированным `seed=42` —
воспроизводимы. Датасет **отсортирован по времени** (не перемешан) —
это важно, см. раздел про утечку данных ниже.

## Как устроена генерация (коротко)

1. У каждого клиента — свой профиль: страна, обычный уровень трат, обычные
   часы активности, известные устройства, любимые категории покупок.
2. Основная масса строк — легитимные транзакции по этим профилям.
3. У ~4% клиентов происходит «угон» карты/аккаунта — короткая пачка
   (3–10 операций за минуты) с типичными признаками мошенничества: другая
   страна, новое устройство, ночное время, высокорисковые категории
   (`electronics`, `crypto_exchange`, `gambling`, `online_marketplace`,
   `jewelry`, `travel`), биполярные суммы (мелкое «прощупывание» карты
   ИЛИ попытка быстро вывести крупную сумму).
4. Метки зашумлены: ~12% реального мошенничества банк «не заметил»
   (`is_fraud=0`, хотя по факту это была мошенническая пачка), и ~0.3%
   легитимных операций ошибочно помечены как мошенничество (спорные
   платежи, чарджбэки по ошибке). Это отражает реальность — метки в
   fraud-данных почти никогда не идеальны.
5. Поверх всего — «грязь», не связанная с мошенничеством напрямую (см. ниже).

## Колонки

| Колонка | Тип в CSV | Описание | На что обратить внимание |
|---|---|---|---|
| `transaction_id` | строка | ID операции | ~0.4% строк — точные дубликаты с повторным `transaction_id` (имитация повторной отправки) |
| `timestamp` | строка | Время операции | ~99% в ISO `YYYY-MM-DDTHH:MM:SS`, ~1% в формате `DD.MM.YYYY HH:MM`, ~0.2% пустые |
| `customer_id` | строка | ID клиента | — |
| `customer_home_country` | строка | Домашняя страна клиента (ISO-2) | ~1% пропусков |
| `card_last4` | число/пусто | Последние 4 цифры карты | ~1% пропусков |
| `amount` | строка(!) | Сумма операции | Смешанный формат: обычно `1234.56`, но ~3% — «по-русски» (`1 234,56`), ~1% — `N/A`, ~0.5% — с ошибочным минусом, ~0.3% — «лишний ноль» (умножено на 100). **Не число по умолчанию — требует парсинга** |
| `currency` | строка | Валюта | В основном `RUB`/`USD`, но ~2% с лишними пробелами или в нижнем регистре |
| `merchant_category` | строка | Категория продавца | ~3% пропусков, ~2.5% — с лишним регистром/пробелами (`" ELECTRONICS "` вместо `electronics`) |
| `merchant_country` | строка | Страна продавца (ISO-2) | Не совпадает с `customer_home_country` — умеренно частый, но НЕ железный признак мошенничества (легитимные поездки/покупки за границей тоже есть, ~3% легитимных операций) |
| `channel` | строка | `POS` / `online` / `mobile_app` / `ATM` | — |
| `device_id` | строка | ID устройства | ~4% пропусков. Новое, ранее не встречавшееся устройство клиента — сильный, но не абсолютный сигнал |
| `ip_country` | строка/пусто | Страна IP-адреса | Заполнена **только** для `online`/`mobile_app` (для POS/ATM это структурно бессмысленно) — отсюда ~50% пропусков в этой колонке. Это **MNAR**-пропуск (Missing Not At Random), не случайный |
| `account_age_days` | целое | Возраст счёта на момент операции, дней | — |
| `customer_avg_amount_30d` | число | Средний чек клиента за 30 дней **до** текущей операции | Посчитан строго по прошлым операциям — не содержит утечки из будущего. Если будете пересчитывать сами — не забудьте про это ограничение |
| `customer_txn_count_1h` | целое | Число операций клиента за 1 час **до** текущей | То же самое — строго прошлое. Резко растёт внутри мошеннических пачек (сигнал скорости/velocity) |
| `is_fraud` | 0/1 | **Целевая переменная** | Зашумлена (см. выше) — это осознанное решение, не ошибка |

## Известные проблемы качества данных (то, что нужно чистить)

- Пропуски: `merchant_category`, `device_id`, `card_last4`,
  `customer_home_country`, `amount` (значения `N/A`), `timestamp` (пустые
  строки), `ip_country` (структурные, см. выше).
- Дубликаты строк по `transaction_id` (~0.4%).
- `amount` — смешанные форматы записи числа, отрицательные значения-опечатки,
  выбросы «лишний ноль».
- Несогласованный регистр/пробелы в `currency` и `merchant_category`.
- `timestamp` в двух разных форматах.

Ничего из этого не подобрано случайно — каждый вид «грязи» встречается в
реальных банковских выгрузках, и разбор с этим — часть учебной задачи.

## Ловушки при построении модели

### 1. Дисбаланс классов — accuracy не показатель

При доле мошенничества ~1.7% модель, которая всегда предсказывает
«легитимно», получит accuracy ≈ 98.3% и будет бесполезна. Смотрите на:

$$\text{Precision} = \frac{TP}{TP+FP}, \qquad
\text{Recall} = \frac{TP}{TP+FN}, \qquad
F_1 = \frac{2 \cdot P \cdot R}{P + R}$$

а также PR-AUC (площадь под кривой precision-recall) — для сильно
несбалансированных классов она информативнее ROC-AUC, который может
выглядеть обманчиво хорошо. Порог классификации (по умолчанию 0.5) почти
всегда придётся подбирать отдельно под бизнес-компромисс между
пропущенным мошенничеством (FN) и ложными блокировками легитимных клиентов
(FP) — это инженерное решение, не математический факт.

Для обучения нейросети на несбалансированных данных — это уже вопрос
метода, не факт: обычно помогает `class_weight`/взвешенная функция потерь,
иногда — undersampling легитимного класса или oversampling
(SMOTE и его варианты); что сработает лучше — стоит проверить
эмпирически на вашем val-сплите, а не выбирать заранее.

### 2. Утечка данных из будущего (temporal leakage)

Датасет отсортирован по времени специально. **Случайный** train/test split
(`train_test_split(..., shuffle=True)`) перемешает будущее с прошлым и даст
искусственно завышенное качество модели, которое не воспроизведётся в
реальности — модель как бы «подглядывает» в будущее клиента при обучении.

Правильно — сплит по времени: например, последние ~2 месяца (`timestamp >=
2026-07-01`) — тест, всё, что раньше, — train/val. Это математический факт
о том, как работает утечка, не вопрос вкуса.

### 3. Признаки, которые сами могут содержать утечку

`customer_avg_amount_30d` и `customer_txn_count_1h` в этом датасете уже
посчитаны без утечки (строго по прошлым операциям). Но если будете
добавлять свои агрегаты (средняя сумма клиента, частота операций и т.п.) —
считайте их так же: только по данным, доступным строго ДО момента
текущей операции. Иначе даже честный time-based split не спасёт.

### 4. Шумные метки — потолок по recall

Поскольку ~12% реального мошенничества помечено в датасете как `is_fraud=0`
(банк их не поймал), ваша модель физически не может достичь recall=1.0 по
этим меткам, даже если она идеально нашла закономерность — часть примеров
просто неправильно размечена. Это нормально и отражает реальность fraud-задач:
метка — это то, что зафиксировал банк, а не абсолютная истина.

## Как пересоздать/изменить датасет

```bash
python3 generate_dataset.py
```

Внутри файла — константы `RNG_SEED`, `N_CUSTOMERS`, `PERIOD_START/END`, доля
клиентов с мошенничеством (`fraud_share` в `gen_fraud_bursts`). Меняйте и
перегенерируйте — весь пайплайн детерминирован при фиксированном сиде.

`eda_check.py` — быстрый прогон для проверки, что в данных виден сигнал
(баланс классов, распределение сумм, доля мошенничества по часам, пропуски
по колонкам) → `eda_overview.png`.
